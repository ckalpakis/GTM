# outbound-agent

Cloudflare Worker in TypeScript with Wrangler and D1. The Worker exposes `GET /health`,
an authenticated Unipile reply webhook, a sender scheduled every 15 minutes, and daily retention cleanup.
Replies are checked for opt-outs before AI classification; interested contacts are
forwarded to a configured GoHighLevel webhook. Sending is disabled by default with zero caps.

## Daily retention cleanup

`cleanupExpiredContacts` in `src/retention.ts` runs on `17 3 * * *` (03:17 UTC daily).
The scheduled handler routes by `event.cron`, independently of the 15-minute sender.
The schedule is registered on deployment; [Cloudflare Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/)
use UTC. No new database migration or secret is required.

Each invocation captures a fixed UTC Unix-second cutoff, then deletes contacts with
`retention_expires_at <= cutoff` in batches of 100, oldest first. Each batch is one
atomic DELETE with a bounded subquery, with no OFFSET. It stops when a batch is short
or after 100 batches (at most 10,000 contacts). The logged result includes `deleted`,
`batches`, `cutoff`, and `hasMore`; a remaining backlog produces a warning and is picked
up by the next daily run. Failed queries propagate so the invocation reports failure;
previously completed batches stay committed and are safe to resume.

`retention_expires_at` is computed at insertion as `collected_at + retention_seconds`.
Database triggers keep both timestamps immutable. Cleanup uses this original deadline,
never `updated_at`, message activity, scoring, reply times, or the current retention setting.
It deletes expired contacts even when they are suppressed. Foreign keys remove their
provenance, messages, provider mappings, and reply records, and clear contact/message
references in send counters. **The job never writes to or deletes from `suppression_list`**;
every permanent suppression entry is preserved, including entries without a contact.

`test/retention.test.ts` covers multi-batch deletion, batch-budget resumption, expiry
boundaries, recent/future last-touch timestamps, dependent cleanup, suppression permanence,
and routing between the two cron schedules.

## Local development

Requires Node.js 22 or newer and npm.

```sh
npm ci
npm run typegen
npm run db:migrate:local
npm run dev
```

Check `http://localhost:8787/health` after the development server starts.

```sh
npm run typecheck
npm test
npm run build
```

Tests run the migrations and typed helpers against an isolated, in-memory D1 database
using Miniflare. They do not use the development or remote database.

## Remote database

```sh
npx wrangler login
npm run db:create
```

Replace the all-zero `database_id` in `wrangler.jsonc` with the ID returned by
`db:create`, then apply the migrations:

```sh
npm run db:migrate:remote
```

`npm run deploy` deploys the Worker when ready. Migration commands explicitly select
local or remote storage. The all-zero ID is a local placeholder, not a provisioned cloud database.

## Schema and queries

- `migrations/0001_initial_schema.sql` creates the four tables, indexes, foreign keys,
  and status/boolean constraints.
- `migrations/0002_compliance_guards.sql` protects suppression records, retention,
  and message eligibility with triggers.
- `src/db.ts` provides typed domain records and parameterized D1 queries.
- `worker-configuration.d.ts` is generated by `npm run typegen`; regenerate after
  changing Wrangler bindings or the compatibility date.

All timestamps are **UTC Unix seconds**. D1 stores booleans as checked integers
(`0`/`1`); the helpers return JavaScript booleans. Contact and message IDs are UUIDs
generated by the helpers. `icp_status` is `pending`, `qualified`, or `rejected`;
`intent_score` is an integer from 1 to 5 for qualified contacts and NULL otherwise. Message status is `drafted`,
`queued`, `sent`, `failed`, or `cancelled`.

```ts
import { Database } from './db';

const db = new Database(env.DB);
const contact = await db.createContact({
  linkedin_url: 'https://www.linkedin.com/in/example',
  name: 'Example Contact',
  source_post_url: 'https://www.linkedin.com/posts/example',
  collected_at: Math.floor(Date.now() / 1000),
  retention_seconds: 30 * 24 * 60 * 60, // Example only: choose your retention policy.
  sources: {
    linkedin_url: 'apify:run-id',
    name: 'apify:run-id',
    source_post_url: 'apify:run-id',
  },
});
const draft = await db.createDraft(contact.id, 'Hello!');
```

`createContact` requires a provenance source for each supplied external field and
inserts contact + provenance in one D1 batch transaction. Provenance has a composite
primary key `(contact_id, field_name)`. Duplicate contacts are rejected; enrichment
must not reset collection time or expiry. Retention is a required input, computed
from the original collection time, and cannot be changed by an update or replacement.

Use `suppress(url, reason)` for opt-outs. It normalizes the LinkedIn profile URL,
preserves the first suppression record, flags matching contacts, and cancels pending
messages. Suppression also applies when a contact is collected again. Suppression
records cannot be updated or deleted with ordinary SQL. Use the helpers for ingestion
and suppression so profile URL variants resolve to the same identity.

`deleteExpiredContacts(limit)` deletes expired contact data and cascades to messages
and provenance. It never deletes suppression records. No cleanup cron is enabled yet;
a future scheduled handler can call this bounded helper.

Drafts include `Reply STOP to opt out.` and start unchecked. After review,
`queueReviewedMessage(id)` requires the footer and an active, unsuppressed contact
with `icp_status = 'qualified'` and a valid 1–5 score. It returns false for unqualified contacts.
Editing checked text requires resetting the message to an unchecked draft. Before
any future provider call, use `getSendableMessage(id)` to recheck eligibility.

Before enabling sending, register the STOP/opt-out webhook described below. Its keyword
check runs **before any AI classification**. The sender records an attempt before calling
Unipile and never automatically retries uncertain sends. An external provider call cannot
be made atomic with a D1 check.

Wrangler setup follows the [Cloudflare D1 documentation](https://developers.cloudflare.com/d1/get-started/).
Queries use [D1 prepared statements](https://developers.cloudflare.com/d1/worker-api/prepared-statements/).

## Source contacts from a LinkedIn post

`src/sourceFromPost.ts` exports the Worker function `sourceFromPost(postUrl: string)`.
It uses the cookieless
[api-ninja/linkedin-post-reactions-scraper](https://apify.com/api-ninja/linkedin-post-reactions-scraper)
Actor, requests all reaction types, waits for a successful run, and paginates its dataset.
The adapter matches that Actor's `reactorName`, `reactorHeadline`, `reactorProfileUrl`,
and `reactionType` fields; other publishers' Actors may have different schemas.

1. Apply `0003_contact_engagement_source.sql` with `npm run db:migrate:local`
   (and `npm run db:migrate:remote` for your provisioned remote database).
2. Copy `.dev.vars.example` to `.dev.vars` and fill in `APIFY_TOKEN` and
   `CONTACT_RETENTION_SECONDS`, a positive integer for your chosen retention policy.
3. For deployment, set the token with `npx wrangler secret put APIFY_TOKEN` and
   put `CONTACT_RETENTION_SECONDS` in Wrangler's `vars` or use
   `npx wrangler secret put CONTACT_RETENTION_SECONDS`.

Call it from an awaited Worker handler:

```ts
import { sourceFromPost } from './sourceFromPost';

const result = await sourceFromPost('https://www.linkedin.com/posts/example-activity-123456789');
// { runId, datasetId, fetched, inserted, skipped, invalid }
```

For explicit dependency injection, use `createPostSource(env)` from `src/sourcing.ts`
to obtain the same single-argument function. This integration does not add a public
HTTP endpoint or automatically run a paid scrape.

New contacts store `source = "apify_post_engagement"`, `reaction_type`, the requested
post URL, and the current collection time in UTC Unix seconds. Supplied fields get
the same source in `provenance`. Suppressed identities and existing contacts are
skipped atomically; subsequent imports preserve the first post, reaction, collection
time, and retention expiry. Invalid/missing profile URLs or reaction types are counted
as `invalid`; missing names/headlines are stored as NULL. Company is not inferred.

The function has a ten-minute invocation deadline and requests a nine-minute Actor
execution timeout. GET requests retry HTTP 429/5xx up to three attempts; creating a
run is never retried automatically. API failures are reported without response bodies
or tokens. Failed, aborted, and timed-out runs are rejected before dataset import.
An import failure after a completed page may leave earlier contacts committed;
rerunning safely skips them, but starts a new paid Actor run.

Await this work for the lifetime of an active request or scheduled invocation; do not
launch it as detached work or assume `ctx.waitUntil()` keeps an HTTP request alive for
ten minutes. For larger jobs, use a durable workflow/webhook to resume ingestion.
The local tests mock Apify HTTP responses and use a real local D1 runtime; they do not
call the paid Actor.

## Score against your ICP

`src/scoreAgainstICP.ts` exports `scoreAgainstICP(contact)`. Pass a stored contact
(or its `id`, `headline`, and `company`). Only headline and company are sent to the
OpenAI Responses API; the contact ID, name, profile URL, and message history stay local.

```ts
import { scoreAgainstICP } from './scoreAgainstICP';

const decision = await scoreAgainstICP(contact);
if (!decision.icp_fit) return; // Always reject, regardless of any model-provided score.
// decision.intent_score is now an integer 1–5.
// Drafting and compliance review are separate; scoring never queues a message.
```

Apply migration `0004_icp_scoring_gate.sql` locally and to your provisioned remote
database. Configure `OPENAI_API_KEY` as a secret and `ICP_CRITERIA` with your target
roles, company types, mandatory requirements, and exclusions. Both are required;
there is no assumed business ICP. `OPENAI_MODEL` is optional and defaults to
`gpt-4.1-mini`. Local examples are in `.dev.vars.example`. For deployed secrets:

```sh
npx wrangler secret put OPENAI_API_KEY
npx wrangler secret put ICP_CRITERIA
```

The prompt requests a boolean fit first and a score only for fits, using
[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
Insufficient evidence means false. Intent is based on explicit buying signals:
1 means no explicit intent, through 5 for immediate purchase intent. Headline and
company alone typically do not establish buying intent.

False is stored as `icp_status = 'rejected'` with `intent_score = NULL`, even if a
model unexpectedly supplies a high score. True is stored as `qualified` only after
validating an integer score in 1–5. Refusals, malformed/incomplete responses, API
errors, or a 30-second timeout throw and leave the started evaluation `pending` with
no score. No provider error bodies or credentials are included in errors.

Starting an evaluation clears prior qualification and cancels queued messages.
Evaluation IDs prevent an older response from replacing a newer decision. The final
write also rechecks suppression, expiry, and the original headline/company. Changed
profile fields require re-scoring. Drafts can exist before scoring, but both helper
queries and SQL triggers prohibit queueing or sending unqualified contacts.

The migration resets old qualifications to `pending` and cancels their queued
messages because the previous 0–100 scale cannot be reinterpreted as 1–5. Existing
rejections stay rejected, and sent-message history is retained. Collection and
retention timestamps do not change. This is contact scoring, not reply classification;
any future reply flow must still check opt-out keywords before calling an AI model.

Tests use `createIcpScorer(env, fetch)` to mock OpenAI responses while persisting
results through local D1. They cover false-with-high-score rejection, queue guards,
invalid responses, errors, suppression changes, and competing evaluations; no paid
OpenAI request is made by the tests.

## Draft a connection note

```ts
import { draftMessage } from './draftMessage';

const message = await draftMessage(contact);
// message.status === 'drafted'; message.compliance_checked === false
```

Apply `0005_drafted_message_status.sql` with the migration commands above. It converts
existing `draft` rows to `drafted`, retaining messages, indexes, foreign keys, and the
suppression/ICP/send guards. The queue helper now accepts `drafted` rows.

`draftMessage(contact)` uses the existing `OPENAI_API_KEY` and optional `OPENAI_MODEL`
(default `gpt-4.1-mini`). It returns the saved `Message`; it does not queue or send it.
The full note is at most 299 UTF-16 code units, including the exact source post URL,
whitespace, and `Reply STOP to opt out.` footer. Links are never truncated.

Only the post URL is stored today, so the note identifies that specific post by link
and does not guess its content, author, or title. The model selects among short,
grounded note variants personalized with the contact's first name when available.
The structured output schema and a local allowlist enforce those variants, preventing
claims about past meetings, conversations, referrals, or relationships. This deliberately
limits wording variation until verified post content is available for richer personalization.

Example (using illustrative stored data):

```text
Hi Jane, I noticed you reacted to this post: https://www.linkedin.com/posts/example. I'd be glad to connect.

Reply STOP to opt out.
```

Suppressed, rejected, expired, missing, or stale contacts fail before the API call.
The insert rechecks eligibility and the supplied contact fields after generation.
Pending ICP contacts may have drafts, but still cannot be queued without qualification
and message compliance review. Missing/invalid post URLs, links too long to fit, output
outside the allowed wording, refusal, incomplete responses, and HTTP/30-second timeout
errors save no message. Nothing is silently truncated or replaced with a fallback.

Tests use `createMessageDrafter(env, fetch)` with mocked OpenAI responses and local D1,
including a populated-database migration check. No paid generation is run by tests.

## Send drafted connection invitations

`src/sendQueuedMessages.ts` exports `sendQueuedMessages()`. The scheduled handler in
`src/index.ts` runs the same implementation on `*/15 * * * *` (every 15 minutes).
The schedule is registered when you deploy; nothing is sent merely by editing the config.

Apply `0006_send_attempts.sql` locally and remotely, then configure:

| Variable | Purpose |
| --- | --- |
| `UNIPILE_DSN` | Your HTTPS Unipile origin, including its assigned port, without `/api/v1` |
| `UNIPILE_API_KEY` | Secret API key |
| `UNIPILE_ACCOUNT_ID` | Your connected LinkedIn account's Unipile ID |
| `DAILY_SEND_CAP` | Maximum send attempts per account per UTC calendar day; zero disables sending |
| `MAX_SENDS_PER_RUN` | N: maximum attempts per cron invocation; zero disables sending |
| `UNIPILE_WEBHOOK_SECRET` | Random secret of at least 32 characters, also configured on the webhook |

Both caps default to zero in `wrangler.jsonc`. Set them to your chosen values after
configuring the account and opt-out webhook. Store credentials with `wrangler secret put`;
`.dev.vars.example` shows local settings. Run `npm run typegen` after binding changes.

The sender reads `drafted` messages for qualified contacts. `checkMessageCompliance`
loads fresh contact/message data, checks permanent suppression and expiry, and requires
the original Apify engagement provenance plus an exact match to the grounded note
variants. Edited notes, invented prior-contact claims, missing opt-out text, missing
provenance, or invalid lengths are blocked. Failed ICP contacts are never sent.

It resolves the recipient's provider ID with Unipile's
[Retrieve a profile](https://developer.unipile.com/reference/userscontroller_getprofilebyidentifier)
endpoint, then uses [Send an invitation](https://developer.unipile.com/reference/userscontroller_adduserbyidentifier)
with `{ account_id, provider_id, message }`. These are connection invitations carrying
the drafted note; this version does not send chat messages or fall back to InMail.

D1 atomically reserves daily capacity and claims the message before dispatch. Multiple
cron runs cannot claim the same message or exceed the daily budget. Each account/contact
is attempted at most once, including when multiple drafts exist. Compliance is rechecked
after profile lookup and immediately before dispatch; `compliance_checked` becomes true
only when the passing draft is claimed. Notes with a recorded attempt cannot be edited.

Only a successful HTTP response with `object: "UserInvitationSent"` and an
`invitation_id` marks the message `sent` and sets `sent_at`. Errors stop the invocation.
Timeouts, network failures, 5xx responses, or unrecognized success bodies are recorded as
`unknown` in `send_attempts` and `failed` on the message; they are **never automatically
retried**. A crash after dispatch may leave an attempt `dispatching` and its message
`queued`; it is also held for reconciliation, not resent. A crash before dispatch can
leave a conservative `reserved` hold. Inspect these records against Unipile before any
manual recovery. If the database write fails after provider acceptance, the attempt remains
held so a subsequent cron invocation cannot duplicate the send.

Reservations, confirmed sends, failures, and uncertain attempts all count toward the
daily cap. This deliberately caps attempts as well as successful sends. The UTC window
is checked again at dispatch. Counters survive contact/message retention cleanup without
retaining message text or profile URLs; the ledger's contact/message references become
NULL. The cap covers this Worker's sends, not activity performed manually or by other apps.
Invocations also stop after ten minutes and scan at most 1,000 drafts.

There is an unavoidable interval between dispatch and provider acknowledgement. An
opt-out already committed before the final check prevents dispatch. A request already
in flight cannot be recalled; if Unipile acknowledges it, the historical send is recorded
even if suppression arrived while awaiting the response. Suppression still blocks all
future sends.

### Wire up the opt-out path before enabling caps

In Unipile, register a `messaging` webhook for your connected account pointing to:

```text
https://YOUR_WORKER_HOST/webhooks/unipile
```

Configure a custom `Unipile-Auth` header containing `UNIPILE_WEBHOOK_SECRET`, plus
`Content-Type: application/json`. Unipile documents custom secret headers in its
[webhook authentication guide](https://developer.unipile.com/docs/webhooks-2).

The endpoint validates the header and account, ignores messages sent by your own account,
and checks STOP, unsubscribe, opt-out, remove-me and similar keywords before any
AI classification. It permanently suppresses both the sender's provider-ID URL and the
mapped contact URL. Provider mappings expire with contact retention; permanent provider-ID
suppression still blocks a later import after its identity is resolved. Ordinary replies
follow the classification flow below. The sender requires the webhook secret, but
registering and verifying webhook delivery in Unipile is still required configuration.

`npm test` mocks all Unipile calls and exercises actual local D1 transactions, overlapping
senders, caps, rejection paths, uncertain responses, retention-safe counters, and opt-out
webhooks. Tests never send a real invitation.

## Classify replies and forward interested contacts

`handleUnipileWebhook` in `src/replies.ts` handles `POST /webhooks/unipile` using
Unipile's [new-message event fields](https://developer.unipile.com/docs/new-messages-webhook).
Apply migration `0007_reply_events.sql` before enabling the updated handler:

```sh
npm run db:migrate:local
# After configuring your remote D1 binding:
npm run db:migrate:remote
npx wrangler secret put OPENAI_API_KEY
npx wrangler secret put GHL_WEBHOOK_URL
```

Set `GHL_WEBHOOK_URL` to the secret HTTPS URL generated by your GoHighLevel workflow's
[Inbound Webhook trigger](https://help.gohighlevel.com/support/solutions/articles/48001237383).
Keep the existing `UNIPILE_ACCOUNT_ID` and `UNIPILE_WEBHOOK_SECRET` configuration above.
Local values belong in `.dev.vars`; `OPENAI_MODEL` defaults to `gpt-4.1-mini`.

After authentication and filtering out your own messages, a case-insensitive keyword
check runs **before any AI call, configuration check for AI/GHL, or event deduplication**.
`stop`, `unsubscribe`, `not interested`, `remove me`, and the other opt-out variants in
`isOptOutReply` immediately write permanent suppression entries and return. This also
applies to message edits and unknown contacts; no OpenAI or GoHighLevel call occurs.

Other new messages are matched to existing contacts using the account/provider mapping
or a canonical LinkedIn profile URL. Unknown, suppressed, expired, empty, and non-opt-out
edited messages are ignored. The handler requires Unipile's `message_id` for classification.
OpenAI receives only the reply text as untrusted data and returns a validated enum using
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs):
`interested`, `neutral`, or `not interested`. Only explicit interest qualifies for a handoff.
A semantic `not interested` classification is recorded without forwarding; the keyword
branch remains responsible for immediate permanent opt-outs.

For interested replies, the Worker rechecks suppression and the original retention
deadline, then POSTs this flat JSON object to GoHighLevel:

```json
{
  "event_id": "reply-event-uuid",
  "unipile_message_id": "unipile-message-id",
  "classification": "interested",
  "contact_id": "contact-uuid",
  "linkedin_url": "https://www.linkedin.com/in/jane",
  "name": "Jane Doe",
  "headline": null,
  "company": "Example",
  "source": "apify_post_engagement",
  "source_post_url": "https://www.linkedin.com/posts/example",
  "collected_at": 1789603200,
  "retention_expires_at": 1792195200,
  "icp_status": "qualified",
  "intent_score": 1
}
```

Map these fields in the receiving workflow. This request starts that workflow; creation
or updating of a CRM contact depends on its configured actions. No email, phone number,
or reply text is invented or included. HTTP 2xx marks the handoff `delivered`, indicating
webhook acceptance rather than completion of downstream workflow actions.

`reply_events` stores classifications and delivery state keyed by account/message ID.
Duplicates reuse the classification and cannot dispatch the same event twice. Classification
failures return 503 and can retry; abandoned classification claims expire after 60 seconds.
A missing/invalid GHL URL returns 503 while retaining the successful classification.
OpenAI and GHL requests have 15-second and 8-second timeouts respectively.

A timeout, HTTP error, or network failure during the GHL POST records `unknown`, logs
only the event ID, and returns 502. Subsequent duplicate events acknowledge the held
record without resending. A crash during dispatch can leave `dispatching` held in the same
way. Inspect these rows against your GHL workflow logs before any manual recovery:

```sql
SELECT id, message_id, status, error_code FROM reply_events
WHERE status IN ('unknown', 'dispatching');
```

The request includes an `Idempotency-Key` equal to `event_id`, but the Worker does not
assume GHL deduplicates that header. Different interested replies have distinct event IDs;
use `contact_id` in your workflow when you want to upsert the same CRM contact.
An opt-out committed before dispatch blocks forwarding; an already in-flight POST cannot
be recalled. Reply metadata is deleted with contact retention cleanup; suppression entries
remain permanent. The handler neither stores raw reply text nor extends contact retention.

`test/replies.test.ts` uses mocked OpenAI/GHL HTTP calls and real local D1 to verify
keyword-first suppression, classifications, concurrent deliveries, retries, opt-out races,
uncertain handoffs, and retention cleanup. No live webhook calls are made by tests.
